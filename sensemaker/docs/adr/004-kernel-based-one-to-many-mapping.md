# ADR-004: Kernel-Based One-to-Many Observation-to-Listing Mapping

## Status
Accepted

## Context
One observation can represent multiple listings:

- **Job boards**: Scrape `company.com/careers` → extract 10 job postings
- **News aggregators**: Scrape newsletter → extract 5 impact stories
- **Email digests**: Parse weekly email → extract multiple opportunities

The system must handle 1:N mapping from Observation → Listing while maintaining provenance.

## Decision

### Kernel processor generates multiple revisions
The **kernel** is the LLM-powered extraction logic that:
1. Takes an observation (raw content + metadata)
2. Applies a schema-specific extraction prompt
3. Returns `List<RevisionPayload>` where each payload represents one listing

### Flow
```
Observation (1)
    ↓
kernel.process(obs)
    ↓
[RevisionPayload, RevisionPayload, ...]  (0..N)
    ↓
Create or link to Listings (N)
    ↓
Create Revisions (N) with observationId reference
```

### Kernel responsibilities
- **Identity extraction**: Determine `Listing.canonicalKey` for each item (e.g., normalized job URL, content hash)
- **Schema validation**: Ensure each payload matches the expected structure
- **Deduplication hint**: Return stable keys so system can upsert listings

### Database operations (per observation processing)
```typescript
const payloads = await kernel.process(observation);

await prisma.$transaction(async (tx) => {
  for (const payload of payloads) {
    // Upsert listing by canonicalKey
    const listing = await tx.listing.upsert({
      where: { canonicalKey: payload.canonicalKey },
      create: {
        kind: payload.kind,
        canonicalKey: payload.canonicalKey,
        // ... other fields
      },
      update: {} // No-op if exists
    });

    // Create new revision
    await tx.revision.create({
      data: {
        listingId: listing.id,
        observationId: observation.id,
        schemaVersion: payload.schemaVersion,
        status: 'PENDING',
        extracted: payload.data
      }
    });
  }

  // Mark observation processed
  await tx.observation.update({
    where: { id: observation.id },
    data: {
      processingStatus: 'DONE',
      processedAt: new Date()
    }
  });
});
```

## Consequences

### Positive
- **Flexible**: Kernel can return 0 (no matches), 1 (simple case), or N (batch) revisions
- **Provenance preserved**: `Revision.observationId` links back to source
- **Idempotent**: Re-processing same observation creates new revisions for same listings
- **Separation of concerns**: Kernel handles extraction, DB handles persistence

### Negative
- **Large transactions**: Processing 50 jobs from one page = 50 inserts in one transaction
- **Observation grouping**: No easy "show me all revisions from one scrape" view
- **Kernel complexity**: Must implement identity logic (canonicalKey generation)

### Schema implications

**No changes needed** to MVP schema, but we clarify semantics:
- `Listing.canonicalKey`: Generated by kernel, must be stable and globally unique
- `Revision.observationId`: Always set (links back to source evidence)
- One observation can create revisions across multiple listings

**Admin UI implications**:
- Observation detail page shows "Generated N revisions across M listings"
- Revision list view can filter by `observationId` to see all extractions from one source
- When reviewing a revision, show link to source observation

### Kernel schema contract
Each kernel must return:
```typescript
interface RevisionPayload {
  canonicalKey: string;    // Unique identifier for the listing
  kind: 'JOB' | 'NEWS';
  schemaVersion: number;
  data: JsonObject;        // Extracted structured data

  // Optional convenience fields
  title?: string;
  orgName?: string;
  sourceUrl?: string;
}
```

### Error handling for one-to-many
If kernel partially succeeds (extracts 5 of 10 items then times out):
1. Create revisions for the 5 successful extractions
2. Mark observation as `DONE` (not FAILED)
3. Store warning in `Observation.lastError`: "Partial extraction: 5 of 10"
4. Operator can retry to get remaining items (kernel should be idempotent)
